# M7 开工与交接：SDK、历史迁移、备份恢复、安全与稳定发布

> 状态：planned。本文定义 M7 的当前进入条件、事实核对、范围边界和实施顺序，不代表 M7 已实现、已发布或已完成旧平台切换。权威工作包细节见 [`2026-09-22-m7-execution.md`](2026-09-22-m7-execution.md)，开发 Agent 提示词见 [`M7-development-agent.md`](../../../prompts/M7-development-agent.md)。原始产品约束以 [`M7-sdk-migration-and-release.md`](../../../roadmap/M7-sdk-migration-and-release.md) 为准。

## 1. 目标与完成定义

M7 将 M1–M6 已形成的 API-first、不可变证据、ScoringPass、ReportRef、Baseline、GateResult 和 exporter v1 交付为可安装、可调用、可迁移、可恢复、可安全发布的产品。它不是重新实现执行器、评分器、Comparison 或 Gate；它是外部消费、历史来源治理、运维保护和旧平台替代的收口阶段。

完整 M7 必须同时满足：

- Python 同步 SDK、CLI、pytest/CI 集成消费公共 API 和 M6 固定契约，不复制服务端数据库或 Gate 算法；
- SDK/CLI 的超时、错误、能力协商、幂等、SSE 游标和本地/远程模式语义可测试；
- wheel、Web 构建、Docker/Compose 和声明支持环境能在干净环境安装或启动，运行不依赖开发者 cwd/PYTHONPATH；
- 历史导入保留 source identity、原始 hash、映射版本、unknown 和不可分发 origin，不将旧记录伪装成新执行；
- dry-run、apply、checkpoint、resume、conflict、rollback 和 artifact staging 都可审计；
- DB 与 Artifact 备份来自一致快照，恢复先到 staging 校验，不能自动执行恢复包中的 queued/running 任务；
- loopback、Origin/Host、认证、TLS、凭据脱敏、retention pin、GC tombstone 和供应链检查均有具体行为证据；
- 支持矩阵、release candidate、升级/回退手册和三类替代场景证据齐备；功能切换与历史迁移分别验收；
- 未验证的 PG、Docker、Provider、Harness、Judge、数据许可或旧平台组合保持 `not_run`、`blocked`、`experimental` 或 `unsupported`，不因代码存在或 CI 总体成功自动宣传为 stable。

## 2. 当前基线与继承事实

实际开发开始时必须重新记录 `git rev-parse HEAD`、分支/worktree、`git status --short`、Alembic head、Python/Node/pnpm、Docker/Compose、PostgreSQL 和远程凭据配置。当前规划参考事实如下：

- M6 已合入主干 merge commit `aee31a9`，提交说明记录了 Experiment、Comparison、Statistics、Baseline、Gate、API/CLI/Web、exporter v1 和 DeepSeek V4.1 Flash 有界验收；开发 Agent 仍需在当前 HEAD 重新核对，而不能只信 merge message。
- `docs/verification/M6.md` 当前仍包含部分目标标记、PG/Docker/Harbor/Judge 校准边界及 GSM8K/DirectLlm 遗留 Web 债务。M7 进入门必须先把 M6 当前证据与主干实际行为对齐，不能将未验证项直接视为发布支持。
- M6 已提供固定的 RunReportRef/ReportSnapshot、GateResult、退出码 0–6、JSON/JUnit exporter v1、Experiment/Baseline/Gate API/CLI/Web 入口。M7 应扩展这些公共契约，不新增平行的报告、Gate、导出或 current 语义。
- 当前已有 `packages/sdk-python/motte_sdk/export.py` 和 `packages/storage/motte_storage/maintenance.py`，但它们是 M6 exporter/早期 SQLite 维护能力的起点，不代表 M7 的可安装 SDK 或一致备份恢复已经完成。
- CI 已包含 uv/pnpm、PostgreSQL service、make check、audit、Trivy 配置检查和 OpenAPI/TypeScript 漂移门；M7 必须验证其实际覆盖，并补充 clean wheel、Compose build/up、恢复、安全和支持矩阵证据。
- 真实旧平台导出、许可证、凭据重绑定、生产 DB、正式 release 和切换窗口不是规划阶段默认可用输入。缺少时使用合成/脱敏 fixture 完成软件验证，真实 apply/cutover 单独授权。

## 3. M7 与 M6/前序阶段边界

| 责任 | M6 已交付 | M7 负责 | M7 不负责 |
|---|---|---|---|
| 结果语义 | ReportRef、ScoringPass、Comparison、Baseline、Gate、exporter v1 | SDK/CLI/pytest 消费与扩展固定引用 | 重写评分、比较、Gate 或重新选择 current |
| 执行 | Experiment 编排既有 Run/Worker | submit/wait/cancel/retry 的远程包装，明确幂等 | 第二套 queue、双写、跨执行器接管旧 Job |
| 历史 | import-like 缺字段策略和 evidence pin | ImportManifest、只读来源导入、迁移审计、恢复/回退 | 把 imported 记录伪装成新运行、补猜历史事实 |
| 运维 | exporter、Baseline pin 语义 | 一致备份、staging restore、retention/GC、安全发布 | 无确认覆盖生产库、按 mtime 删除 pinned 证据 |
| 发布 | M6 离线/CLI/Web/live 证据及已知限制 | wheel、Compose、升级回退、支持矩阵、RC、三场景切换 | 多租户/RBAC/Kubernetes、多语言 SDK、长期双库同步 |

## 5. 独立 worktree、协作和授权

M7 实现必须在 `.worktree/m7-sdk-migration-release` 下使用独立分支，例如 `codex/m7-sdk-migration-release`。主工作区只用于最终集成；不得覆盖其他任务的 dirty 文件、已有 worktree 或 `var/` 证据目录。

主 Agent 应使用子 Agent 分担 SDK contract、SSE、CLI parity、packaging、migration、backup/security、Web 和只读 review。共享 contract、migration、API main、maintenance、CI/Compose 和生成文件同时只能有一个写入负责人。子 Agent 交付必须由主 Agent 审阅 diff、运行目标测试并写入验证记录。

默认离线测试不调用真实模型、Judge、Benchmark、旧业务工具或生产数据库。用户已授权的 DeepSeek V4.1 Flash 只能用于完成软件闭环后的有界 live smoke，并需先确认 model/profile/provider、样本、调用/Token/费用/时限和凭据引用；不能用 live 结果代替确定性测试。真实旧数据 apply、生产备份恢复和旧平台切换需要单独操作授权。

## 7. 进入门与退出门

进入门：当前 HEAD、M6 evidence summary、migration head、dirty 文件、SDK/API/OpenAPI/TS 状态、Docker/PG 可用性、旧数据/许可证/凭据条件均已登记；T00 协议冻结；所有新增测试能正常收集。

退出门：23 个目标、12 个工作包、21 个验收场景和非编号要求均有实现、真实消费者、行为测试和证据；clean install/wheel、SDK/CLI/SSE/pytest、导入/恢复/备份、安全/retention、发布矩阵和三替代场景分别完成；失败、skip、blocked、not_run 不混为 passed；历史导入与功能切换分别得出结论。缺少真实旧数据或生产授权时可输出 `implementation_complete / offline_verified / live_pending`，但不能输出 `cutover_ready` 或 `stable_supported`。
