# M8 Persistent Judge Calibration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an auditable import → review → preflight → bounded ScoringJobs → Worker → report → exact qualification lifecycle, and verify that qualification independently inside selected-Pass Gates; quality-Gate closure remains conditional on an approved metric contract.

**Architecture:** Keep immutable calibration versions, human review events, execution requests, reports and qualification sources in the existing store. Compile only server-owned inputs into the existing ScoringJob/Invocation system; reconstruct reports from its actual durable ledger. Gates verify a qualification source pinned when the selected Judge Pass was created, never a client flag or the in-memory registry.

**Tech Stack:** Python, Pydantic, FastAPI, existing SDK/CLI and WorkerLoop, Memory/SQLite/PostgreSQL, Alembic, pytest; no new dependencies.

**Spec:** `docs/superpowers/specs/2026-09-30-m8-persistent-closure-design.md`, section B and delivery gates. Inspected baseline: `50b806d`; its full verification is being handled separately, not claimed by this plan.

- Preserve `policy_for()`/`validate_policy()` exactly: 30 human-reviewed samples, six of each existing kind; disagreement/error/refusal maxima 0.15; missing-evidence maximum 0.25; repeat and swap requirements enabled with minima 1.0. Do not add request-level threshold overrides.
- Keep `JudgeProviderPolicy.max_calls_per_job=32` and automatic model retries disabled. Split a calibration into bounded children; authorize and enforce the aggregate budget before persisting any child.
- Tests use explicitly labelled software fixtures and scripted providers. They establish software behavior, never real human/model acceptance.

## Review Gate and Additional Contract Decision

**Do not implement until the user reviews this plan.** The lifecycle design was approved; the following positive-path detail needs explicit acceptance during that review:

Current human gold is boolean per criterion, but pairwise Judge output is a candidate preference or tie. All current policies require swaps, and `JudgeSpec` hashes include mode. The public subject compiler supports only single mode. Pairwise qualification therefore needs additive typed gold and server-resolved subject pairwise inputs (Tasks 1, 3, 5); one mode cannot borrow another's qualification.

A second, independent boundary is verified in the code: `pairwise_metrics()` emits `passed=None`; `report_snapshot()` derives existing quality metrics from Boolean outcomes; neither Gate metric registry defines pairwise quality. **A trustworthy Judge qualification only satisfies the qualification rule. It does not provide a quality metric or make either Gate pass.** Never coerce preferences to Boolean accuracy, reinterpret lexicographic candidate order as quality, or omit the quality rule.

A third approval-dependent detail affects qualification itself: policies require six `missing_evidence` samples. When required evidence is correctly enforced, those calls have no scored winner; requiring `status=ok` plus a winner for every swap makes 1.0 consistency impossible. Proposed typed exception: human gold explicitly declares a non-scored outcome; two distinct, completed successful Provider invocations count as repeat/swap-consistent only when both deterministic parses exactly match that expected non-scored status. Both directions remain in the denominator. No winner is invented, `None` is not a tie, and missing/refusal/error rates still count those outcomes under the existing maxima. For six missing-evidence samples among 30 with equal criterion count, missing-evidence rate remains 0.20, not zero. Unsettled/failed/indeterminate calls never qualify as expected non-scored outcomes. This is an explicit outcome-consistency semantic addition requiring the same user plan approval; without it, qualification remains ineligible. The separately owned required-evidence parser repair is a prerequisite, not permission to change calibration semantics.

Review choice:
- **A. Bounded partial acceptance / diagnostic-only fallback:** approve typed pairwise gold, the explicit expected-non-scored consistency rule above, three-way confusion and same-Run/same-case saved-attempt references. Implement the six tasks below. Only after all these semantic additions are approved may pairwise qualification be eligible; quality Gates remain fail-closed with an explicit unsupported metric reason; single-mode remains experimental under current swap policy. The original positive quality-Gate/M8 closure remains OPEN, explicitly recorded in delivery evidence.
- **B. Full requested software closure (recommended):** approve A’s typed gold and expected-non-scored consistency semantics plus the explicit pairwise quality contract below, and execute Tasks 1–9 in this same plan. Tasks 7–9 fully specify the metric, source reconstruction, comparison limits and both quality Gates; no separate unwritten implementation plan or additional serial plan approval is required. This is a material new metric/denominator/policy design covered by the current consolidated review, not by the earlier lifecycle approval.

Scope B contract for this review: `pairwise_challenger_score@1`, unit=`ratio`, direction=`gte`, denominator=`planned_pairs`, missing policy=`fail_closed`. Freeze explicit challenger/reference attempt roles before execution; presentation A/B and lexical IDs never define roles. An overall challenger win earns 1, reference win 0, explicit tie 0.5; require successful complete criterion outcomes. Average distinct planned calls within each pair, then equally average all planned pairs. Any absent/duplicate/failed/indeterminate call, missing role, empty plan or incomplete pair makes the metric unavailable; repeats/orders cannot inflate the pair denominator. Freeze roles, plan/call digest, formula version, planned/valid pair counts and coverage in a typed pairwise report section, leaving Boolean `accuracy` unavailable and `passed=None` unchanged. New Gate policies explicitly reference this metric/version and a user-supplied threshold; there is no invented default threshold or reuse of a calibration threshold. Preserve historical metric/policy meanings, version registry/report/Gate semantics as required, and reject baseline-delta/critical-case modes for this metric until separately defined. Both Gate implementations must verify full planned-pair coverage and trusted qualification before evaluating the selected quality threshold.

Scope B acceptance tests in Tasks 7–9 cover challenger-role reversal, presentation reversal invariance, tie=0.5, unequal repeat counts with equal pair weighting, partial/empty plans, unknown results, missing criteria, old-policy compatibility and real positive/negative quality thresholds through both public Gates on all three stores. Expected example: pair means `[1.0, 0.5, 0.0]` yield `0.5` over three planned pairs; a test-only explicit threshold 0.6 fails while 0.4 passes, only with complete evidence and valid qualification. This is a proposed policy decision, not a software test result or authorization to run models.

## Review Focus

1. Reused version labels across calibration IDs or changed policy/provider content must never resolve another qualification (Tasks 1, 5).
2. Pairwise ties/order/missing criteria stay distinct from binary outcomes; valid calibration qualification cannot manufacture an available quality metric (Tasks 1, 4, 5).
3. A crash between child creation, dispatch, response settlement and report publication must not leak a partial group or rebill (Tasks 2–4).
4. Human names/timestamps are declared provenance inside deployment authorization, not independently verified identity (Tasks 1, 6).
5. Old/manual Passes and independently pinned evidence must survive current-pointer changes, backup, GC and rollback without gaining new qualification (Tasks 2, 5).
