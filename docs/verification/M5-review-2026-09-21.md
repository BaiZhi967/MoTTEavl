## 1. 新增代码发现

### F01 · P1 · Judge 的 token／费用硬上限没有被执行

- 位置：`packages/evaluators/motte_eval/judge.py:1654`；`packages/sdk-python/motte_sdk/scoring_jobs.py:361`；请求构造 `judge.py:882`。
- 预检依赖调用者填写的估算值，默认可以是 0；`spec.budget.hard_cost_cap_usd` 未参与费用比较，却用于声明 `hard_monetary_cap=True`。请求输出上限取自可选 parameters，执行循环没有落实剩余 token／费用额度。
- 已复现：显式授权 `max_total_tokens=0`、`hard_cost_cap_usd=0`，仍执行一次模拟模型请求，记录 150 tokens、估算费用 0.0025 USD，并标记 completed。另一输入预算 cap=0、预估费用 0.001，预检仍报告可执行且存在硬上限。
- 修复：从冻结的真实请求与价格快照计算可证明上界，提交和每次 dispatch 前核对／预留额度，限制 Provider 实际输出；不能提供硬保证的能力明确拒绝硬预算请求，不能把估算称为硬上限。

### F02 · P1 · Judge 预检计划与实际调用计划不一致

- 位置：`packages/sdk-python/motte_sdk/scoring_jobs.py:460`、`:502`。
- pairwise 未显式给 order 时，先收集所有 pair 的顺序，再对每个 pair 遍历全部顺序，产生笛卡尔扩展。两个任务使用相同候选 ID、授权和预算均为 2 次，预检 2 次，实际 4 次且 completed。不同候选 ID 的任务还可能被错误的排列校验拒绝。
- 同源的另一个缺口：`repeats=3` 会进入预检和 fingerprint，但实际只生成一次请求，随后 completed。
- 修复：生成唯一的不可变调用计划，包含 pair、order、repeat 和唯一 call ID；预检、授权、fingerprint、执行与校准均消费该计划。运行前后核验实际调用数不超过授权。

### F03 · P1 · 外部 Run 的 Observation 可以发布成当前 Run 的评分

- 位置：`packages/sdk-python/motte_sdk/scoring_jobs.py:502`。
- `_prepare_inputs()` 未核对字典 case key、请求 owner 与 Observation 的 run/case 身份，也缺少 source pass 与目标 Run 的一致性校验。
- 已复现：请求 `run-1/case-1`，输入 Observation 属于 `FOREIGN/foreign-case`，最终给 `run-1/case-1` 发布 passed=true。后续 Invocation 按请求身份构造，无法补救原证据归属错误。
- 修复：从服务端保存的指定 pass／Observation 解析证据，校验 owner、case、attempt、hash 与引用链；发现不匹配时零调用、零发布。

### F04 · P1 · 人工修订存在 current 指针的 CAS 窗口

- 位置：`packages/evaluators/motte_eval/calibration.py:994`。
- 先读 current，再独立读取 Run revision。若另一修订在中间完成，当前请求仍用旧 current 验证用户期望，却使用新的 revision 写入。
- 确定性交错复现：两个请求都要求 `expected_current_pass_id=pass-source`，先后都成功，较晚请求把较新的 current 覆盖成自己的 pass。旧 pass 未被删除，但用户要求的并发前置条件被绕过。
- 修复：在同一存储事务中比较 expected current 与 revision，再追加 ScoreSet/pass、审计事件和推进 current；Memory、SQLite、PostgreSQL 语义一致。

### F05 · P1 · 实际 Target 和工具执行没有受步骤期限约束

- 修复：deadline 贯穿模型、工具和事件的执行边界，在可能阻塞／产生副作用的地方使用可确认停止的受控执行；禁止以返回后检查耗时替代真实期限。

## 4. 代码质量判断

可保留的基础包括结构化 DSL、无 eval 条件求值、内容 hash 和版本资源、调用账本阶段、独立 ScoreSet/pass、fixture 所有权，以及 UI 对未知／不可用状态的显式表达。本轮组件测试复跑证实这些不是单纯空壳。

主要薄弱点是模块间协议没有用公共链路测试约束：deadline 计算后丢弃、权限编译后没有执行消费者、pass 中存在身份但比较读错位置、校准覆盖规则存在但资格计算未调用、Provider 错误类别拼写不同。测试大量直调原语、构造理想 manifest 或使用脚本 Target，因而“测试多且通过”与用户流程可靠性之间仍有距离。

应优先统一这些协议并增加消费者级反例，不宜在修复期做大规模无关重构。确需拆分大模块时，以调用计划、证据解析、预算预留和评分发布等清晰责任拆分，并保留行为测试。Web 主包体积是后续优化项，不应抢占本轮正确性修复。
